# 01 - Repository layout

Everything sits in one repository, **one directory per API version**: the authored source documents,
the artefacts generated from them (this bundle among them) and the tools. Folder names say what a
folder is for; every folder that a maintainer touches has a `README.md`.

```
<repo-root>/
├── manifest.json                     version index: every vN.N/ directory, which is latest, where its artefacts are
├── README.md                         repository entry point: layout, pipeline, quick start
├── CLAUDE.md / AGENTS.md             pointers for AI coding agents -> tools/api-agent/
├── .gitignore                        ignores dist/ and tarballs
├── <VERSION>/                        ONE DIRECTORY PER API VERSION (v2.0 today)
│   ├── manifest.json                 this version's inventory: domains, groups, okf/postman slugs and titles, common_ref
│   ├── md/                           SOURCES - narrative reference, one folder per domain, one file per group
│   │   ├── 01 · Organization Management/ORG_INFO_AND_SETTINGS.md
│   │   ├── 02 · User & Groups/{ORG_USERS,CUSTOM_ROLES,WORKSPACE_USERS,WORKSPACE_GROUPS}.md
│   │   ├── 03 · Workspace Management/{WORKSPACE_OPERATIONS,WORKSPACE_FOLDERS,WORKSPACE_PREFERENCES,DOMAIN_AND_WHITE_LABEL}.md
│   │   ├── 04 · Data Modeling & Schema/{TABLE_AND_SCHEMA,COLUMNS,LOOKUPS_AND_RELATIONSHIPS,QUERY_TABLES,FORMULA_COLUMNS,AGGREGATE_FORMULAS,WORKSPACE_VARIABLES}.md
│   │   ├── 05 · Data Operations/{SYNC_DATA_IMPORT,ASYNC_DATA_IMPORT,SYNC_DATA_EXPORT,ASYNC_DATA_EXPORT,ROW_OPERATIONS,DATA_SYNC_AND_CONNECTIVITY}.md

│   │   ├── 09 · Schedules & Alerts/EMAIL_SCHEDULES.md
│   │   └── 10 · DSML/AUTOML_ANALYSIS.md
│   ├── zenesis-oas/                  SOURCES - OpenAPI 3.1 + x-zenesis-*, one file per domain (10 files)
│   │   └── common/zoho-analytics-api-common.json      OAuth scopes, Error schema, common responses

│   ├── okf/                          GENERATED by tools/okf/build_okf.py - THE BUNDLE; deleted and rebuilt on every build; committed
│   └── postman/                      GENERATED by tools/postman/build_postman.py - collection + environment

│   │   ├── build_okf.py              generator: <VERSION> sources + handwritten -> <VERSION>/okf
│   │   ├── validate_okf.py           OKF conformance + link + provenance checks
│   │   ├── handwritten/<VERSION>/    SOURCES - hand-authored concepts copied into the bundle on every build (README inside)
│   │   │   ├── overview.md                 -> bundle /overview.md
│   │   │   ├── how-to-use-this-bundle.md   -> bundle /how-to-use-this-bundle.md
```

The bundle directory is `<VERSION>/okf/`; the bundle's own name, as declared in its `manifest.json`, is
`zoho-analytics-rest-api-v2`. Publishing is a copy of this directory into `<VERSION>/` of the public analytics-okf repository.

## Who writes what

| Folder | Written by | Edited by agents? |
|---|---|---|
| `<VERSION>/md` | API documentation authors | **Yes** - this is where endpoint facts change. |
| `<VERSION>/zenesis-oas` | Exported from the Zenesis documentation system; edited here since | Yes, when adding operations, schemas, examples or error codes. Keep valid JSON. |
| `<VERSION>/zenesis-oas-samples` | Same | Yes, when adding SDK snippets for a new operation. |
| `<VERSION>/zenesis-oas/common/zoho-analytics-api-common.json` | Same | Rarely: only for a new OAuth scope or a new common error example. |
| `<VERSION>/manifest.json` | Maintainers | Yes: a new group or domain starts here (folder, slug, `(md, tag)` pairs, `okf` and `postman` blocks). |
| `tools/okf/handwritten/<VERSION>/` | Bundle maintainers | **Yes**, for cross-cutting rules and playbooks. |
| `tools/okf/build_okf.py` | Bundle maintainers | Yes, but only its configuration tables in normal operation. |
| `<VERSION>/okf/` | `build_okf.py` | **Never.** |
| `<VERSION>/oas/` | `tools/zenesis-oas` (`make to-analytics`) | **Never** by hand, except `oas/common/`, which is placed by hand and never regenerated. |
| `<VERSION>/postman/` | `tools/postman/build_postman.py` | **Never.** |

## Two pairs that must stay in step

1. **A markdown endpoint section and its OpenAPI operation.** The generator joins them by title:
   the markdown `## N. Title` must equal the operation's `x-zenesis-title` (or `summary`), or be
   listed in `TITLE_MAP` in the builder. The markdown supplies the narrative, CONFIG tables, samples,
   notes and error tables; the OpenAPI supplies the operation ID, path, scopes, parameters, content
   types, success status, schemas, throttles and its own error list.
2. **A group and its domain.** Every markdown file belongs to exactly one domain folder and one
   OpenAPI file. The mapping is the `domains` list in `<VERSION>/manifest.json` (its `okf` blocks); group and domain slugs become
   directory names in the bundle.

## Things that are deliberately *not* sources

- `<VERSION>/okf/` (generated).
- Anything outside this repository (older `PRD/` folders, zip archives). They are unrelated to this pipeline.
