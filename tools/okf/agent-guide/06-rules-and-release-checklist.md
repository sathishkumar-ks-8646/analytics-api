# 06 - Invariants, forbidden content, versioning, and release checklist

## Invariants that must hold

These are enforced by `tools/okf/validate_okf.py` (exit code 1 on any error) unless marked "convention" —
a rule the generator or sources rely on but that isn't independently checked.

| Invariant | Enforced by |
|---|---|
| Every non-reserved `.md` in the bundle has YAML frontmatter with a non-empty `type`. | validator |
| `index.md` and `log.md` carry no frontmatter, except the bundle root `index.md`, which carries `okf_version: "0.2"`. | validator |
| No `{{` placeholder survives into the built bundle. | validator |
| No `generated.by` key appears in any frontmatter. | validator + `frontmatter()` in the builder |
| Every `resource:` value is either an `http(s)` URL or a bundle-relative path that exists. | validator |
| Every markdown link resolves to a file that exists, and every `#anchor` resolves to a heading in that file (error-catalog anchors `#error-<code>` are trusted without a heading check). | validator |
| Every directory has an `index.md` (warning, not a hard error). | validator |
| `operationId` is unique across every OpenAPI file. | convention — join key for endpoint file names, catalog, SDK docs, manifest |
| `## N.` numbering in a markdown group file is contiguous, since `#N-slug` intra-file links depend on it. | convention |
| A markdown `## N. Title` and its OpenAPI `x-zenesis-title` (or `summary`) match exactly, or a `TITLE_MAP` entry bridges the difference. | convention — otherwise the build prints a WARN and the two are not joined |
| SDK sample JSON keys match the OpenAPI path template and lower-case method exactly. | convention — otherwise the operation gets no SDK Example |
| `<VERSION>/okf/` and `dist/` are never hand-edited. | convention — both are deleted and regenerated by their respective tools |

A clean run looks like:

```
endpoints=168 groups=33 errors=278 sdk=166
```
from `build_okf.py`, followed by
```
errors=0 warnings=0 broken_links=0
```
from `validate_okf.py`. Any `WARN` or `unresolved links:` output from the build, or any non-zero count
from the validator, means the sources need fixing before the result is trusted — do not package or
release past that point.

## Things that must never appear

- **Internal system details in prose**: Java class names, XML security attribute names, template
  names, or file names belonging to the internal documentation system. Endpoint text should read as
  if written for an external API consumer, not for someone touring the authoring tool.
- **Hand-written links to the error catalog.** Use a backticked 4-to-6-digit code in prose (e.g.
  `` `7104` ``) and let `link_error_codes` auto-link known codes; a hand-written link will not match
  the generator's `#error-<code>` anchor scheme reliably.
- **`generated.by`** in any frontmatter block.
- **Unexpanded `{{NOW}}` / `{{BUILDER}}` placeholders** in the built bundle — these are only valid
  inside `handwritten/**/*.md` before the copy step expands them.
- **Edits inside `<VERSION>/okf/` or `dist/`.** Both are wholesale-replaced by their
  generators; anything written there by hand is silently discarded on the next run.
- **Content from outside this repository (older `PRD/` folders, zip archives).** These are unrelated to this pipeline and
  are not sources.

## Versioning

Two version numbers exist and mean different things — don't conflate them:

| Name | What it is | Where it lives | How it changes |
|---|---|---|---|
| `OKF_VERSION` | The Open Knowledge Format spec version this bundle conforms to (currently `0.2`). | Root `index.md` frontmatter (`okf_version`) and `manifest.json`. | Only changes if the bundle adopts a newer OKF spec — not a routine release action. |
| `BUNDLE_VERSION` | The content version of this specific bundle (API docs, endpoints, etc.). | Read from the `OKF_BUNDLE_VERSION` environment variable, else the version already in `<VERSION>/okf/manifest.json`, else `1.0.0`. Also written into `manifest.json` by `bundle_manifest()`. | Set per release, either via the environment variable before `build_okf.py`, or via `--version` on `package_okf.py` (which overrides the version in the packaged copy only, without needing to touch the builder). |

No semantic-versioning policy is defined in the tooling itself — decide the bump according to your
team's own convention for what counts as a breaking, additive, or fix-only change to the docs.

## Release checklist

```bash
cd <repo-root>

# 1. Regenerate the bundle from current sources
python3 tools/okf/build_okf.py
# → must print "endpoints=… groups=… errors=… sdk=…" with no WARN lines.
#   Fix "no OAS operation for markdown endpoint", "OAS operation without markdown section",
#   or "unresolved links:" before continuing.

# 2. Validate the bundle
python3 tools/okf/validate_okf.py
# → must end "errors=0 warnings=0 broken_links=0".

# 3. (Optional) preview what the public copy would change
git -C dist/analytics-okf status

# 4. Package the public distribution
python3 tools/okf/package_okf.py --tarball --version X.Y.Z
# → assembles dist/analytics-okf/ (README.md, llms.txt, LICENSE.md, CHANGELOG.md, okf/, tools/validate.py, .github/)
#   and, with --tarball, dist/analytics-okf-X.Y.Z.tar.gz.
# Other flags as needed: --repo-url, --site-url, --docs-url, --base-url, --ref, --out.
# Re-packaging preserves dist/analytics-okf/.git — the working tree is replaced, history survives.
```

Notes on step 4:
- The README and `llms.txt` templates bake in the URL flags. Their defaults (`DEFAULT_REPO`, `DEFAULT_SITE`,
  `DEFAULT_DOCS`, `DEFAULT_BASE_URL` at the top of `package_okf.py`) are the published values, so a plain
  run is correct; do not pass placeholders. While the bundle is served from the temporary repository,
  `DEFAULT_BASE_URL` points raw-file links there and the `git clone` line and "Canonical copies" footer
  keep the permanent `DEFAULT_REPO`. When the repository moves, set `DEFAULT_BASE_URL = None`.
- The `CHANGELOG.md` template in `package_okf.py` only describes the first release. For every release
  after that, either hand-edit `CHANGELOG.md` in `dist/analytics-okf/` after packaging, or extend
  the template in `package_okf.py` (`changelog()`).
- Committing and pushing `dist/analytics-okf/` is a manual step after packaging — none of the
  three tools perform `git commit` or `git push` themselves.
