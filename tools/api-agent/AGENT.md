# API agent - update every Zoho Analytics API artefact from input markdown

You are an AI agent working in the `analytics-api` repository. You have been given one or more
markdown documents that describe Zoho Analytics REST API endpoints: new endpoints, changed CONFIG
attributes, new error codes, corrected behaviour, a whole new API group. The documents can have any
layout (an API team hand-off, a draft reference page, release notes). Your job is to make this
repository reflect them **completely**: the authored sources first, then every artefact that is
generated from the sources, with every validator green at the end.

Read this file top to bottom once. Then follow the phases in order. Do not skip Phase 3.

## What is where (one directory per API version)

```
<VERSION>/manifest.json         inventory: domains, groups, (md, tag) pairs, okf/postman slugs, common_ref
<VERSION>/md/                   SOURCE  narrative reference, one folder per domain, one file per group
<VERSION>/zenesis-oas/          SOURCE  OpenAPI 3.1 + x-zenesis-* keys, one file per domain
<VERSION>/zenesis-oas/common/   SOURCE  zoho-analytics-api-common.json (scopes, Error schema, common responses)
<VERSION>/zenesis-oas-samples/  SOURCE  SDK snippets per path + method, 9 languages
<VERSION>/oas/                  GENERATED by tools/zenesis-oas        (oas/common/ is placed by hand - never touch it)
<VERSION>/okf/                  GENERATED by tools/okf/build_okf.py
<VERSION>/postman/              GENERATED by tools/postman/build_postman.py
tools/okf/handwritten/<VERSION>/   SOURCE  cross-cutting OKF concepts (foundations, workflows) - edit when a shared rule changes
tools/postman/api-reference-links.json   SOURCE  endpoint title -> public docs page (curated)
```

`<VERSION>` is `v2.0` unless told otherwise. Read `manifest.json` at the root to see which versions
exist and which is `latest`. Never mix versions: a change belongs to exactly one `vN.N/`.

## The rules

1. **An API fact lives in three source files; change all three together.** The group document in
   `md/`, the operation in `zenesis-oas/`, the snippets in `zenesis-oas-samples/`. A fact that is in
   one and not the others produces artefacts that contradict each other.
2. **Never edit generated directories by hand** (`oas/` except `oas/common/`, `okf/`, `postman/`).
   They are deleted and rebuilt. Change the source and rebuild.
3. **Never touch `<VERSION>/oas/common/zoho-analytics-api-common.json`** and never change the
   `https://raw.githubusercontent.com/zoho/analytics-oas/...` URLs that the published specifications
   `$ref`. The maintainer places that file by hand. The Zenesis side `$ref`s the URL in
   `common_ref` of `<VERSION>/manifest.json`; the converter swaps the two.
4. **Titles are the join key.** The markdown heading `## N. Title` must equal the operation's
   `x-zenesis-title` (else `summary`) character for character, or the OKF build emits `WARN` and the
   endpoint document has no schema. If the input uses a different title, pick one and apply it to both,
   or add a `TITLE_MAP` entry in `tools/okf/build_okf.py` when the two must stay different.
5. **Only the vendor keys that have rules.** The `x-zenesis-*` keys allowed in the specifications
   are the ones in `tools/zenesis-oas/rules.json` (mirrored by `KNOWN_VENDOR_KEYS` in
   `tools/validate_api_docs.py`). Do not invent a new one; use `x-zenesis-sections` for notes,
   `x-zenesis-statuscodes` for error tables (on the success response), `x-zenesis-security` for
   throttles, `x-zenesis-enums-desc` for enum labels.
6. **Error responses are `4XX` and `500`**, each a `$ref` to `CommonErrorResponse` and
   `UnexpectedErrorResponse` at `common_ref`. Never `default`.
7. **Write for an external developer.** No internal class names, template names, or authoring-system
   details in any prose.
8. **Do not guess facts.** If the input does not say which scope, permission, status or error code
   applies, look for the same fact on a sibling endpoint in the same group and say so in your summary.
   Leave a clearly marked `TODO` rather than inventing a value - the validators will not catch an
   invented one.
9. **Keep the sources' voice.** Copy the shape of the neighbouring section, operation or sample
   exactly (table columns, bold case headings, `**HTTP NNN**` response labels, example naming).
   `tools/okf/agent-guide/03-source-document-format.md` is the parser's contract.

## Phase 0 - orient

```bash
cat manifest.json                                    # versions; which is latest
python3 tools/api-agent/pipeline.py --check          # is the tree green before you start? (it should be)
python3 tools/api-agent/plan.py --version v2.0 <input1.md> [<input2.md> ...] --json /tmp/plan.json
```

`plan.py` reads the inputs, finds every endpoint they describe, matches each one against the
version's specifications and prints a table: **NEW** (no such method + path), **EXISTING** with the
differences it could detect (title, scopes, CONFIG fields missing from the schema, error codes missing
from `x-zenesis-statuscodes`), the group it belongs to and the three files to edit. Read the whole
report. It is a starting point, not the truth: it cannot see a changed sentence, a renamed field or a
behavioural note, so read the input yourself for those.

If the input is about something other than endpoints (a shared rule, a new OAuth scope, a new data
center, a glossary term), the plan will be empty; go to Phase 2, step F.

## Phase 1 - decide

For each endpoint in the plan decide one of:

| Case | You will |
|---|---|
| NEW endpoint, group exists | Add a section, an operation and a samples entry (Phase 2, A). |
| NEW endpoint, group or domain does not exist | Add the group/domain to the manifest first (Phase 2, D), then A. |
| EXISTING, attribute / field / enum changed | Edit the request or response table in the section and the schema in the operation (Phase 2, B). |
| EXISTING, error code added or changed | Edit the `### Error Codes` table and `x-zenesis-statuscodes` (Phase 2, C). |
| EXISTING, behaviour / permission / limit changed | Edit the prose, the attribute table, `x-zenesis-sections`, `x-zenesis-security` as appropriate. |
| Deprecated or removed | Phase 2, E. |
| Contradiction between the input and the repository | The input is the API team's source of truth **for the facts it states**. Apply it, and list every contradiction you resolved in your summary so a human can confirm. |

Write the decision list down before editing. If the input covers more than ten endpoints, work one
group at a time and run Phase 3 after each group.

## Phase 2 - edit the sources

The detailed procedures are the OKF agent guide's playbooks; they apply to the whole repository, not
only to the bundle: `tools/okf/agent-guide/04-change-playbooks.md`. In short:

**A. New endpoint.** `python3 tools/api-agent/scaffold.py --version v2.0 --title "..." --method ...
--path ... --group "<tag>" [--scope ...] [--config query|form|multipart|none] [--success 200|204]`
prints three skeletons already wired to the conventions. Append the markdown section at the end of
the group file (so no existing `## N.` moves) and add its row to the `## Index` table. Add the
operation under `paths` and its schemas under `components.schemas` of the domain specification; reuse
`#/components/parameters/*` where they exist. Add the samples entry keyed by the exact path template
and lower-case method, all nine languages (`Curl`, `C#`, `Go`, `Java`, `Php`, `Python`, `Node`,
`Ruby`, `Deluge`); model each snippet on a neighbouring operation's snippet in the same file. Fill
every `TODO`. Add the endpoint's public docs URL to `tools/postman/api-reference-links.json` if one
exists (else leave it out; the Postman request will say "newly added").

**B. Attribute or field.** Edit the row in the section's request block (`### CONFIG Parameters` or
whichever name the file already uses) or `### Response Fields`; mirror it in the operation's CONFIG
schema (`components.schemas.<X>Config`) or response schema; keep `x-zenesis-enums-desc` positionally
aligned with `enum` when an enum changes; fix samples and sample responses that show the old shape.

**C. Error code.** Add the row to `### Error Codes` (first cell the numeric code, a backticked
`UPPER_SNAKE` constant at the start of the reason if known); add `{name, description, resolution}` to
the success response's `x-zenesis-statuscodes`; if the HTTP status matters, add a sample response
labelled `**HTTP NNN ...**` directly above a ```json block containing `"errorCode": N`. Never write a
link to the error catalog by hand.

**D. New group or domain.** Add the entry to `<VERSION>/manifest.json`: for a group `{ "md": STEM,
"tag": "Tag", "okf": { "slug": "kebab", "title": "Title" } }` under the right domain; for a domain a
new object with `folder` (`NN · Title`, consecutive number, middle dot U+00B7), `slug`, `groups`,
`okf` and `postman` (`emoji`, `title`, `covers`). Then create the group file (H1, preamble, `## Index`,
sections), the tag in the specification's top-level `tags[]` with a description, and the samples file.
`python3 tools/validate_api_docs.py --strict` names whatever is still missing.

**E. Deprecate or remove.** Deprecate: `"deprecated": true` on the operation and a note in the
section. Remove: delete the section, the operation and the samples entry; renumber `## N.` if the
section was not last and fix every `#N-slug` link and the `## Index`; remove dangling `TITLE_MAP`,
`MD_ONLY_OPS`, `ID_SOURCES` entries in `tools/okf/build_okf.py`; search other group files for links
to it.

**F. Shared rule** (authentication, headers, criteria syntax, roles, data centers, enums, glossary,
a new scope). Edit the hand-written foundation under `tools/okf/handwritten/<VERSION>/foundations/`;
a new scope goes into `<VERSION>/zenesis-oas/common/zoho-analytics-api-common.json` (the Zenesis
side only - see rule 3) and the maintainer mirrors it to `oas/common/`. A new multi-endpoint
procedure is a new file under `handwritten/<VERSION>/workflows/`.

While editing, keep JSON valid (2-space indent, trailing newline) and keep key order close to the
neighbours so the diff stays reviewable.

## Phase 3 - build everything and make it green

```bash
python3 tools/api-agent/pipeline.py --version v2.0
```

The pipeline runs, in order, and stops at the first failure:

| Stage | Command | Must end with |
|---|---|---|
| sources | `tools/validate_api_docs.py --strict` | `errors=0 warnings=0` |
| oas | `make -C tools/zenesis-oas check` then `to-analytics` then `compare` | `All checks passed`, then `No differences.` |
| okf | `tools/okf/build_okf.py` then `tools/okf/validate_okf.py` | no `WARN`, `errors=0 warnings=0 broken_links=0` |
| postman | `tools/postman/build_postman.py` | `requests=N domains=N sections=N` |
| status | `git status --short` | the list of files you changed, for review |

Fix the **source** for every failure and re-run; `--from okf` skips the stages that already passed.
Typical messages and what they mean:

- `WARN no OAS operation for markdown endpoint: <title>` or `OAS operation without markdown
  section` - the titles differ (rule 4).
- `x-zenesis-... <-- NOT IN rules.json` - an unknown vendor key (rule 5).
- `remote $ref ... does not match common_ref` - a copied `$ref` points at the wrong URL (rule 3).
- `unresolved links:` - a markdown link to a heading or legacy file name the builder cannot resolve.
- `API Endpoint has empty api.permission_required` / `empty permission cell` - the section has no
  `**Permission Required**` row.
- `frontmatter is not valid YAML` - a hand-written concept's title or description contains `: `;
  quote it.
- `round trip lost data` - the vendor-key content changed; `make -C tools/zenesis-oas overlays` then
  commit the regenerated `overlays/<VERSION>/`.
- Postman `--check` reports `STALE` - you edited a source after the last build; rebuild.

When the OKF bundle's content changed, bump its version deliberately:
`python3 tools/api-agent/pipeline.py --version v2.0 --from okf --bundle-version 1.5.0`
(minor for additions, patch for corrections, major for removals or renames).

## Phase 4 - review and hand over

1. `git diff --stat` - the source files you meant to change, plus the regenerated `oas/`, `okf/`,
   `postman/`. Nothing under `oas/common/`. If `overlays/` changed, that is expected after a
   vendor-key edit.
2. `git diff -- <VERSION>/md <VERSION>/zenesis-oas <VERSION>/zenesis-oas-samples` - read your own
   edits once more as the parser would.
3. Add an entry to `CHANGELOG.md` under *Unreleased*: what changed, in terms of endpoints and
   attributes, and which input document it came from.
4. Report to the human: the endpoints added or changed, every contradiction you resolved (rule 8 and
   Phase 1), every `TODO` you had to leave, and the pipeline's final line. Commit only if asked, in one
   commit with the sources and the regenerated artefacts together, so history says which source
   produced which output.

## Quick reference

```bash
python3 tools/api-agent/plan.py --version v2.0 in.md         # what do the inputs mean for the repo?
python3 tools/api-agent/scaffold.py --version v2.0 --title T --method M --path P --group TAG
python3 tools/api-agent/pipeline.py --version v2.0           # build + validate everything
python3 tools/api-agent/pipeline.py --version v2.0 --check   # validate only, write nothing
python3 tools/validate_api_docs.py --strict --version v2.0   # the sources alone
make -C tools/zenesis-oas compare VERSION=v2.0               # zenesis-oas vs oas
python3 tools/okf/build_okf.py --version v2.0 && python3 tools/okf/validate_okf.py v2.0/okf
python3 tools/postman/build_postman.py --version v2.0
```

Reference documents, in the order you will need them:
`tools/okf/agent-guide/03-source-document-format.md` (what the parsers expect),
`tools/okf/agent-guide/04-change-playbooks.md` (procedures),
`tools/zenesis-oas/docs/CONVERSION.md` (what each `x-zenesis-*` key becomes),
`tools/okf/agent-guide/05-builder-internals.md` (the builder's configuration tables),
`<VERSION>/README.md` (the inventory of that version).
