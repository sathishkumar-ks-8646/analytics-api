Importing data

Synchronous, batched and job-based imports, with the limits and response shapes for each.

Three modes, chosen by file size and whether you need to wait for the result.

ModeFile sizeBlockingUse when
Synchronousup to 20 MBYesSmall files where you want the row counts immediately.
BatchedanyYesLarge CSV files; the SDK splits and uploads them for you.
Asynchronous jobanyNoLarge files where you want to poll for completion.

Warning

Do not load data row by row

Add Row costs one API unit per row. Importing a file costs far less and is dramatically faster. Use the row APIs for corrections, not for loading.

Import types#

ValueBehaviour
APPENDAdd every row. Duplicates are kept.
TRUNCATEADDDelete all existing rows, then add.
UPDATEADDUpdate rows matching the configured key, add the rest.

Note

UPDATEADD needs a matching column

Set matchingColumns in the config, otherwise the server cannot tell which rows to update and the call fails validation.

Sample response#

Warning

A successful import can still skip rows

status is success whenever the request was processed. Compare successRowCount against totalRowCount and inspect importErrors — rows with unparseable values are skipped silently otherwise.

Batched import#

For files over 20 MB. The SDK splits the file, uploads each batch, and returns a job id.

Batch size is counted in rows. Keep each resulting batch under 100 MB.

Sample job response#

jobStatus is one of JOB NOT STARTED, JOB IN PROGRESS, JOB COMPLETED or JOB FAILED.

Note

Driving the batches yourself

If you have already split the file, the batch endpoint can be driven directly: send batchKey: "start" with importType and autoIdentify on the first batch, reuse the returned batchKey on the rest, and set isLastBatch: true on the final one to commit the job.
