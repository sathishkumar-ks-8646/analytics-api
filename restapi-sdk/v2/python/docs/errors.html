Failure handling

Errors

The response envelope, HTTP statuses, and the error codes worth branching on.

The failure surface#

ServerError (.errorCode, .message) and ParseError.

The response envelope#

The API has exactly three response shapes.

ShapeHTTPBody
Success with data200{"status":"success","summary":"...","data":{...}}
Success, nothing to return204Empty.
Failure4xx, 5xx{"status":"failure","summary":"<CONSTANT>","data":{"errorCode":<int>,"errorMessage":"..."}}

Synchronous export endpoints are the exception: on success they return the file itself with a matching Content-Type, and only use the JSON envelope on failure.

A failure response#

Branch on errorCode. summary is a stable constant you can log, and errorMessage is localised prose — log it, do not parse it.

Warning

Not every 400 is permanent

Concurrency guards (18072, 7429, 8132) come back as HTTP 400 but are retryable once the operation they are guarding finishes. Retrying them immediately in a tight loop will not help; waiting will.

A retry policy that works#

  • Retry 500s and the concurrency guards above, with exponential backoff.
  • Retry once after a 401, having refreshed the token — but if you are constructing one client and reusing it, the SDK has already done this.
  • Never retry 400 (other than the guards), 403 or 404. The request or the caller is wrong; repeating it just burns API units.
  • Back off for the full lockout when throttled. See Limits.
