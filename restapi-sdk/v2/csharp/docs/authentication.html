Credentials

Authentication

OAuth tokens, scopes, data centers — and the token throttle that breaks integrations which construct a client per request.

Every request carries an OAuth 2.0 access token. The SDK obtains and refreshes that token for you from the client ID, client secret and refresh token you supply — but how often you construct the client determines whether that works or gets you blocked.

Critical

The single most common way to break this SDK

Constructing a new AnalyticsClient for every request — per web request, per cron tick, per job — discards the access token each time and forces a new one. Zoho Accounts allows ten access tokens per ten minutes per refresh token. Cross it and token creation is blocked for the next ten minutes, and every call fails with access denied.

Construct the client once, at application startup, and reuse that instance.

The access token throttle#

Zoho Accounts throws an access denied error when more than ten access tokens are generated within ten minutes using the same refresh token. Once that threshold is reached, Zoho Accounts blocks access token creation for the next ten minutes.

This matters specifically for SDK users. Whenever you initiate the client constructor, the existing access token is discarded and a new one is created on the next API call. A service that builds a client per request therefore mints a token per request, and crosses the limit after ten requests.

To avoid this, initiate the client object only once — during server startup, as a module-level value, or behind a singleton — and use that same instance throughout. The same access token is then used for all API calls. When the token expires after an hour, the SDK handles regeneration itself.

Reference: https://www.zoho.com/analytics/api/v2/authentication/refresh-token.html

This comes from Zoho Accounts, not from the Analytics API, so it does not use the usual Analytics failure envelope and does not carry an Analytics errorCode. That is the signal you have hit the token throttle rather than an API error.

Note

Why one instance is safe

The token the client holds is valid for one hour. The SDK checks for expiry on each call and regenerates the token in place when needed — which is one token per hour, far below the limit. Sharing the instance is what keeps you under it.

Refresh token limits#

LimitValueWhat happens when you cross it
Access tokens per refresh token10 per 10 minutesaccess_denied from Zoho Accounts; creation blocked for 10 minutes.
Access token lifetime1 hour (expires_in: 3600)The SDK regenerates it on the next call.
Refresh tokens per client, per user20Creating a 21st silently deletes the oldest, breaking whatever used it.

Refresh tokens do not expire on their own and do not change when used. Treat them as permanent credentials until explicitly revoked.

Scopes#

Request the union of scopes across every endpoint your integration calls. Prefer the narrowest set that works.

ScopeCovers
ZohoAnalytics.data.allReading and writing row data.
ZohoAnalytics.metadata.allViews, columns, folders, workspace structure.
ZohoAnalytics.modeling.allFormulas, query tables, alerts, schedules.
ZohoAnalytics.share.allSharing and permissions.
ZohoAnalytics.usermanagement.allUsers, roles, admins.
ZohoAnalytics.embed.allEmbed URLs, private links, publishing.
ZohoAnalytics.fullaccess.allEverything. Avoid unless you genuinely need it.

Each .all scope can be narrowed to .read, .create, .update or .delete.

Warning

A token missing a scope fails at call time, not at construction

An under-scoped token constructs fine and fails on the first call that needs the missing scope, with HTTP 401 and error code 8535. Scope problems therefore look like authentication problems. Check the scopes on the token before assuming the credentials are wrong.

Warning

Tokens are bound to their region

A token issued by accounts.zoho.eu is rejected by analyticsapi.zoho.com with error 8535. If authentication fails for no apparent reason, confirm the region first — find it from the URL you use to sign in to Zoho Analytics in a browser.

Using a token you already hold#

If another part of your system manages tokens, hand the SDK an access token directly instead of letting it mint one.

You are then responsible for refreshing it before it expires.

Authorisation is a separate check#

A valid token proves who is calling. Whether that user may perform the operation is checked separately against their organization role, workspace role and view permissions. Those failures return HTTP 403 with error code 7301, not a 401 — the token is fine; the user is not allowed.
